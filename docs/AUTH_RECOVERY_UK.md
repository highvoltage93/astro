# Вхід і відновлення пароля

Редакція: 17.11.2026. Реалізовано в коді; локальні тести, збірка, Docker та
міграції під час цієї роботи не запускалися. Це не підтвердження готовності
реальної поштової доставки до production.

## Межі етапу

- Захист входу від перебору, обмеження реєстрації та запитів відновлення.
- «Забули пароль?» і форма нового пароля з підтвердженням.
- Старі акаунти, поточні паролі та матеріали не змінюються.
- Підтвердження email при реєстрації не потрібне й не реалізоване.
- Листи про оплату/закінчення підписки додаються з модулем оплати пізніше.
- JWT залишається у сховищі браузера. Перехід на HttpOnly/Secure cookie,
  CSRF-захист і керування окремими сесіями є наступним етапом після HTTPS.

## Обмеження спроб

| Дія | Ключ | Ліміт | Вікно |
| --- | --- | --- | --- |
| Вхід | IP | 30 | 15 хвилин |
| Вхід | Нормалізоване ім'я користувача, незалежно від IP | 10 | 15 хвилин |
| Реєстрація | IP | 5 | 1 година |
| Запит відновлення | IP | 10 | 1 година |
| Запит відновлення | Нормалізований email | 3 | 1 година |
| Встановлення нового пароля | IP | 10 | 15 хвилин |

Вікно фіксоване, починається з першої спроби. Рахуються всі спроби, не лише
невдалі; успіх не обнуляє лічильник. Ліміт знімається автоматично після строку,
подальші спроби не продовжують строк. Ліміти зберігаються в PostgreSQL і не
скидаються від перезапуску API. Атомарний UPSERT захищає від паралельного обходу.

Відповідь при перевищенні: HTTP 429 із `Retry-After` у секундах. Форма показує
час очікування. Ліміт за email повертає звичайну HTTP 202 без нової відправки,
щоб не розкривати, які адреси використовуються. При відмові БД лімітів
операція повертає 503, а не пропускається без контролю.

Ключі лімітів: HMAC-SHA256 від типу операції й нормалізованого ідентифікатора
з `JWT_SECRET`. Таблиця не містить відкритих IP, username чи email. Прострочені
рядки прибираються порціями до 1000 під час запитів, не частіше разу на хвилину.
Це не повний захист від DDoS: перед відкритим платним запуском потрібні також
контроль навантаження на проксі й моніторинг. Ліміт username може тимчасово
обмежити й власника акаунта, якщо зловмисник цілиться саме в нього.

### IP за проксі

Локально `trustProxy=false`: довільний `X-Forwarded-For` ігнорується.
У VPS compose `AUTH_TRUST_PROXY_CIDRS=uniquelocal`, оскільки API не має публічного
порту і доступний через Caddy у приватній Docker-мережі. Caddy має перезаписувати
клієнтські forwarded-заголовки. Не публікуйте порт API з таким налаштуванням;
для іншої мережі задайте конкретні довірені CIDR. Не ставте глобальне `true`.
При додаванні CDN/тунелю перевірте довірений ланцюжок IP окремо: інакше всі
користувачі можуть потрапити під один IP-ліміт.

## Відновлення

1. `POST /auth/forgot-password` приймає email. Однакова відповідь для наявного
   й невідомого акаунта. Пошук акаунта та SMTP виконуються асинхронно.
2. PostgreSQL-черга `auth_mail_jobs` тимчасово містить адресу. Worker перевіряє
   чергу кожні 2 секунди; завдання має блокування 60 секунд, до 5 спроб
   доставки з паузами. Завершені завдання видаляються, прострочені прибирає worker.
3. Адреса шукається без урахування регістру. Якщо старі дані містять кілька
   акаунтів із такою адресою в різному регістрі, лист не відправляється.
   Адміністратор має розв'язати дублювання, а не обирати випадковий акаунт.
4. Токен має 32 випадкові байти. У БД лише SHA-256, строк дії 30 хвилин від
   запиту, ID користувача, email і поточна версія доступу. На акаунт один
   чинний токен: нова видача замінює попередній, зокрема при повторній доставці.
5. Посилання формується з `APP_ORIGIN`, не з заголовка Host. Токен знаходиться
   у fragment `#token=...`, тому не надходить у URL запиту чи access-лог проксі.
   Форма прибирає fragment із рядка адреси й тримає токен лише в пам'яті.
   Після перезавантаження форми потрібно знову відкрити посилання з листа.
6. `POST /auth/reset-password` перевіряє новий пароль за правилами реєстрації:
   8–128 символів, велика й мала літери, цифра, спеціальний символ.
7. Serializable-транзакція споживає непрострочений токен, перевіряє email
   і версію доступу, зберігає хеш пароля, збільшує `authVersion`, записує аудит.
   Повторне використання токена не допускається. Автоматичного входу немає.

SMTP timeout може означати, що провайдер прийняв лист, але не підтвердив це.
Повторна спроба може надіслати ще один лист із новим токеном. Використовуйте
останній чинний лист; гарантія exactly-once для SMTP не заявляється.

Після відновлення або зміни пароля адміністратором попередні JWT відхиляються
на наступному захищеному запиті. Уже відкритий екран не видаляється дистанційно.
Токени старих користувачів без поля `ver` вважаються версією 0, тому міграція
сама по собі не розлогінює їх. Зміна email адміністратором анулює reset-токен.

## Локальна пошта без домену

Звичайний `docker-compose.yml` містить Mailpit. API відправляє на внутрішній
порт `mailpit:1025`; реальні листи в інтернет не йдуть. Перегляд пошти:
`http://localhost:8025` після наступного запуску локального compose.

HTTP-порт Mailpit прив'язаний лише до `127.0.0.1`, SMTP назовні не опублікований.
Поштова скринька без постійного тому; обмежена 100 повідомленнями/24 годинами.
Не запускайте цей dev-compose як production і не публікуйте Mailpit.
Для нестандартного фронтенд-порту змініть `APP_ORIGIN` у локальному `.env`.

## Production

`EMAIL_TRANSPORT=disabled` за замовчуванням: логін і ліміти працюють, посилання
«Забули пароль?» приховане, прямі reset-запити повертають 503.

Після HTTPS і вибору SMTP-провайдера заповнити в `deploy/vps/.env`:

```ini
EMAIL_TRANSPORT=smtp
MAIL_FROM=noreply@YOUR_DOMAIN
SMTP_HOST=SMTP_PROVIDER_HOST
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=SMTP_USERNAME
SMTP_PASSWORD=SMTP_SECRET
```

Для порту 587 обов'язковий STARTTLS (`SMTP_REQUIRE_TLS=true` у compose).
Для implicit TLS провайдера: порт 465 і `SMTP_SECURE=true`.
`APP_ORIGIN` у production compose береться як `https://${SITE_HOST}`.
Сертифікати SMTP перевіряються. Налаштуйте відправника та DNS за вимогами
провайдера; паролі SMTP не додавайте в Git. На поточному HTTP/IP листи не вмикати.

Міграція `20261117000000_auth_recovery` додає поля користувача й три таблиці,
нічого не видаляє. Її потрібно виконати **до запуску нової API**, навіть коли
пошта вимкнена. Поточний VPS deploy виконує migrate-сервіс автоматично; локальний
dev-compose використовує `db:push`. Не замінюйте production-міграції на db:push.

## Перевірки перед увімкненням

Написані тести `auth-security.test.ts` і `password-reset.test.ts` входять у
наявний CI-шаблон `tests/*.test.ts`. Вони використовують підставні залежності,
не SMTP чи живу БД. Під час цієї роботи їх не запускали.

Окремо перевірити в погодженому тестовому середовищі: конкурентні SQL-ліміти
й одночасне споживання токена на PostgreSQL, міграцію існуючої БД, IP через
Caddy, доставку/повтор SMTP, Safari й мобільну форму, старий логін і відкликання
токенів після reset. Не оголошувати пошту production-ready до цих перевірок.
