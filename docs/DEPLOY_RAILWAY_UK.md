# Розгортання Astroprocessor: Railway + Neon

## Стан підготовки

У репозиторії додано конфігурації production-збірок, початкову міграцію та задачу резервного копіювання. Ресурси у провайдерів ще не створені, URL не видані, секрети не налаштовані. Docker-збірки, тести, підключення до БД та реальне відновлення в цій ітерації не запускалися. Це підготовка до першого деплою, не підтвердження готового production.

Локальний `docker-compose.yml` та звичайні Dockerfile залишаються для розробки. Production використовує окремі `Dockerfile.production`, без dev-серверів, bind mounts та автоматичного `prisma db push`.

## Схема

```text
Браузер -> Railway web (Next.js) -> Railway api (Fastify + Swiss Ephemeris)
                                           |
                                           +-> Neon PostgreSQL через TLS

Railway backup (cron) -> пряме підключення Neon -> pg_dump -> age -> зовнішній S3
                                       моніторинг запусків -> зовнішній dead-man monitor
```

База не знаходиться у файловій системі контейнерів Railway. Контейнери можна перебудовувати без перенесення даних. Незалежний бекап зберігається поза Railway та Neon. HTTPS не замінює авторизацію, а публічна адреса бети не обмежує доступ лише тестувальниками.

## 1. Облікові записи

Потрібні Railway, Neon, S3-сумісне сховище іншого провайдера та зовнішній сервіс моніторингу з Healthchecks-сумісним ping API (`/start`, `/fail`, успішний ping базового URL). Увімкнути MFA, зберегти recovery codes окремо. Підключити тільки необхідний GitHub-репозиторій.

Neon і Railway обрати у близьких європейських регіонах. План Neon має підтримувати бажане вікно PITR; увімкнути його явно та перевірити в панелі, не покладатися на значення за замовчуванням. Для початку ціль — 7 днів історії. Тарифи та ліміти уточнювати перед оплатою.

## 2. Нова база Neon

Для першого порожнього production використати PostgreSQL 16, як у локальному Compose, щоб не поєднувати деплой зі зміною major-версії БД. Створити окремий production-проєкт/базу. Тестове середовище не повинно використовувати production credentials.

Зберегти два URL:

- Pooled URL для `DATABASE_URL` API, з `sslmode=require`, `connection_limit=5` та `pool_timeout=20`.
- Direct URL без `-pooler` для `MIGRATION_DATABASE_URL`; міграції працюють напряму.

Паролі з URL-спецсимволами мають бути закодовані. Не записувати credentials у Git, Dockerfile, звичайну документацію або скриншоти. Приклади без секретів є в `deploy/railway/*.env.example`.

Початкова міграція `apps/api/prisma/migrations/0_init/migration.sql` згенерована Prisma 5.18 з поточної схеми без підключення до БД. На новій порожній базі `migrate deploy` створює таблиці. Міграція не створює користувача admin.

### Якщо треба перенести поточні дані

Не запускати початкову міграцію навмання на заповненій базі. Спочатку зробити й перевірити копію; зупинити запис на джерелі на час фінального перенесення. Відновити повний дамп в окрему порожню Neon-базу. Порівняти фактичну структуру з поточною Prisma-схемою.

Лише якщо структури узгоджені, позначити baseline як застосований (з кореня репозиторію; `DATABASE_URL` у цьому сеансі має бути direct URL цільової бази):

```bash
corepack pnpm --filter @astroprocessor/api exec prisma migrate resolve --applied 0_init --schema prisma/schema.prisma
```

Ця команда змінює історію міграцій і сама не перевіряє повну відповідність структури. Не застосовувати її автоматично до будь-якої наявної БД. Якщо дамп уже містить коректну `_prisma_migrations`, повторна baseline-операція не потрібна. Після перенесення окремо перевірити користувачів, карти, прогнози, консультації та історію редакцій.

## 3. Сервіси Railway

Створити порожній проєкт і три сервіси з одного GitHub-репозиторію. Root Directory залишити коренем репозиторію для всіх: pnpm workspace потребує `packages/`. У Settings вказати відповідний Config File Path:

| Сервіс | Config File Path | Публічний порт |
| --- | --- | --- |
| api | `/deploy/railway/api.json` | 4000 |
| web | `/deploy/railway/web.json` | 3000 |
| backup | `/deploy/railway/backup.json` | Не публікувати |

Не додавати сторонні Start Command поверх команд образів. При використанні змінного `PORT` погодити його зі значенням Target Port у Networking. API та web слухають `0.0.0.0`. Установити одну репліку на старті; горизонтальне масштабування важких синхронних розрахунків потребує окремого плану.

Вимкнути автодеплой до завершення налаштування першого запуску. Спочатку створити сервіси, задати порти та згенерувати їхні домени через Settings -> Networking -> Generate Domain, потім додати взаємні URL та запустити деплої. Якщо панель вимагає спочатку deployment, дозволено отримати домен після першої невдалої спроби; не послаблювати production-перевірки через тимчасовий HTTP або dev-секрет.

### API variables

Взяти `deploy/railway/api.env.example`, замінити всі заглушки. `CORS_ORIGIN` — точний HTTPS origin фронтенду без кінцевого `/`. Новий JWT-секрет можна згенерувати локально:

```bash
openssl rand -hex 32
```

Pre-deploy виконує `node apps/api/scripts/migrate-deploy.mjs`. Він передає direct URL лише процесу Prisma та запускає `migrate deploy`. Помилка міграції має блокувати новий деплой. Команда не містить `reset`, `db push` чи `accept-data-loss`.

API image збирає ядро, генерує Prisma Client і завантажує ефемериди під час build. На старті production відсутні ефемериди або обов'язкові env спричиняють помилку, а не запуск із dev-налаштуваннями. Healthcheck `/health/db` перевіряє підключення до БД; він не є перевіркою точності астрологічних розрахунків.

### Web variables

Взяти `deploy/railway/web.env.example`. `NEXT_PUBLIC_API_URL` — точний HTTPS origin API без кінцевого `/`. Railway передає змінну у Docker build через оголошений `ARG`. Вона вбудовується у браузерний JavaScript: зміна вимагає **нової збірки**, не лише restart.

Фронтенд використовує Next.js standalone output тільки в production Docker-збірці. Healthcheck `/login`. Наразі директорії `public` у web немає; якщо з'являться статичні файли там, додати її копіювання у runtime stage.

### Доступ і домени

Після успішного деплою користувачі відкривають видану адресу `https://<web>.up.railway.app`. Купувати домен не потрібно. Окремий API URL є публічним, оскільки браузер звертається до нього напряму; Neon credentials знає лише сервер.

Власний домен додається пізніше через Railway Custom Domain та DNS-записи з панелі. Після зміни адрес оновити `CORS_ORIGIN`, `NEXT_PUBLIC_API_URL`, перебудувати web та передеплоїти API. Міграція домену сама по собі не переносить або видаляє дані.

## 4. Незалежні резервні копії

Образ задачі містить PostgreSQL 18 client, який може створювати дамп PostgreSQL 16; не вибирати сервер новішої major-версії за клієнт. Backup URL повинен бути direct libpq URL без Prisma-параметрів `schema`, `connection_limit`, `pool_timeout`. Права backup-role мають дозволяти читати всю прикладну БД, включно з майбутніми таблицями; будь-яка помилка pg_dump завершує задачу помилкою. Дамп не включає глобальні ролі сервера; при відновленні їх відтворюють окремо.

1. Створити приватний bucket в іншого провайдера. Доступ не повинен залежати лише від Railway або Neon акаунта.
2. Видати задачі S3 credentials тільки для GetObject/PutObject та потрібних multipart-операцій у вибраних prefixes. Не давати DeleteObject, зміну lifecycle чи адміністрування bucket. Увімкнути versioning/Object Lock за підтримки провайдера; вони можуть збільшувати витрати.
3. Згенерувати ключ age на довіреному комп'ютері з установленим age:

```bash
age-keygen -o astro-backup.agekey
```

Приватний ключ зберегти у менеджері паролів і другій захищеній копії. На Railway передається тільки публічний recipient `age1...`. Втрата приватного ключа робить дампи невідновлюваними. При ротації зберігати старі ключі, доки існують старі копії.

4. У bucket налаштувати lifecycle: `astro-production/daily/` — видалення через 14 днів, `astro-production/monthly/` — через 100 днів (приблизно три місячні копії, іноді чотири). Застосувати до дампів і `.sha256`, а також налаштувати строки noncurrent versions і очищення незавершених multipart uploads, якщо потрібно. Скрипт навмисно нічого не видаляє сам.
5. Створити зовнішній monitor: очікується успіх щодоби, grace period 2 години, повідомлення на email/інший канал. Перший запуск monitor активувати вручну, щоб відсутність навіть першого бекапу не залишилася непоміченою. Додати його секретний ping URL у `BACKUP_HEALTHCHECK_URL`.
6. Заповнити variables з `deploy/railway/backup.env.example`. Для AWS S3 можна не задавати `BACKUP_S3_ENDPOINT`; для іншого S3-провайдера вказати його HTTPS endpoint і відповідний region.
7. Запустити задачу вручну і перевірити появу зашифрованого об'єкта та повідомлення monitor. Розклад у конфігурації: `15 2 * * *`, щодня о 02:15 UTC. Задача завершується, не працює постійно; максимальна тривалість 45 хвилин.

Алгоритм: `pg_dump -Fc` -> потокове шифрування age -> upload -> повторне завантаження зашифрованого об'єкта та порівняння SHA-256 -> checksum file -> success ping. Незашифрований дамп не записується на диск задачі. Логи не друкують URL підключень або ключі. Тимчасові зашифровані файли очищаються при нормальному завершенні/помилці.

Першого числа задача також пише `monthly/`. Якщо запуск пропущено, зробити ручний із `BACKUP_MONTHLY=1`, потім прибрати цю змінну. При відсутності/зависанні cron сповіщає зовнішній monitor. Недоступність monitor теж робить job неуспішним, навіть якщо файл уже завантажився; повторний запуск створить нове унікальне ім'я.

Копії містять персональні дані й хеші паролів. Не зберігати їх у публічному bucket, GitHub artifacts або Git. Upload/readback перевіряє цілісність передачі, **не повноцінне відновлення БД**.

## 5. Відновлення і навчальна перевірка

Перед відкриттям доступу та потім щомісяця відновити копію в окрему **порожню тестову БД**, не у production. Завантажити `.dump.age` та відповідний `.sha256` у приватну локальну директорію. З тим самим PostgreSQL client 18 і age:

```bash
sha256sum -c BACKUP.dump.age.sha256
age --decrypt -i /secure/path/astro-backup.agekey -o restored.dump BACKUP.dump.age
pg_restore --list restored.dump
pg_restore --dbname="$RESTORE_DATABASE_URL" --no-owner --no-acl --exit-on-error --single-transaction restored.dump
```

`RESTORE_DATABASE_URL` має бути окремим direct URL для тестового відновлення. Команди показані як інструкція й автоматично не виконуються. На macOS замість sha256sum можна використати `shasum -a 256 -c`. Приклад не містить `--clean`: він не повинен видаляти наявні дані. Незашифрований локальний файл після перевірки прибрати з урахуванням політики захисту пристрою.

Перевірити кількість користувачів/карт/консультацій, історію редакцій, логін тестового користувача, відкриття збереженої карти та консультації в ізольованому застосунку. Записати дату перевірки та час відновлення. Тестове середовище не повинно надсилати повідомлення реальним користувачам. Зафіксувати, що відновлення може використовувати старий код/схему: підбирати відповідний Git commit перед оновленням міграцій.

Ціль: незалежний щоденний дамп із максимальною втратою приблизно доби змін, PITR — для точнішого відновлення в межах його фактичного вікна. Реальний RTO визначається навчальним відновленням, а не припущенням.

## 6. Наступні релізи та відкат

- Після успішного першого запуску ввімкнути GitHub auto-deploy для обраної гілки. Несумісні API/web зміни випускати поетапно, не покладатися на одночасний деплой.
- Майбутні schema-зміни оформлювати новою міграцією у локальній/тестовій БД та комітити SQL. Не змінювати `0_init` після першого застосування.
- Перед небезпечною міграцією створити свіжий бекап і перевірити PITR. Автоматичний pre-deploy сам не гарантує наявність свіжого дампу.
- Відкат контейнера не відкочує БД. Використовувати сумісні expand/contract міграції. Не запускати автоматичний destructive rollback.
- API graceful shutdown закриває HTTP-сервер і Prisma; довгі синхронні розрахунки все ще можуть затримати обробку сигналу.
- Налаштувати зовнішній uptime monitor. Railway deploy healthcheck не замінює постійний моніторинг.
- Установити бюджетні сповіщення. Жорсткий ліміт витрат може зупинити сервіс; вибрати цей компроміс свідомо.

## Перед відкритим запуском

Окремо потрібні: реальні production build/runtime перевірки, контрольні астрологічні fixtures, аудит доступу до даних, захист логіну/дорогих розрахунків від зловживань, оновлення застарілих залежностей (зокрема Next.js 14.2.7) після оцінки сумісності, заміна тестових паролів, підтвердження ліцензії Swiss Ephemeris. Ця підготовка не підміняє ці роботи. До них не відкривати production для реальних клієнтських даних.
