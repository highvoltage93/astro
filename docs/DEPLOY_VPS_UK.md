# Production на VPS: Ubuntu 24.04, Docker Compose, Caddy

## Статус і межі

Цей комплект підготовлено для Server.ua: 2 vCPU, 4 GB RAM, 50 GB SSD, Ubuntu 24.04 amd64. На сервер ще не підключалися: IP, SSH-доступ і домен не надано. Збірки, тести, Docker та реальні backup/restore перевірки в цій ітерації не запускалися за попередньою домовленістю. Це не сертифікація готовності до відкритого production.

Схема: Caddy -> Next.js та `/api/*` -> Fastify -> PostgreSQL 16. Назовні опубліковані тільки 80/443; SSH працює на хості. PostgreSQL, міграції та API використовують окрему внутрішню мережу. База в persistent volume, TLS-сертифікати Caddy також у volumes. Railway і Neon для цього варіанта не потрібні, попередні конфігурації збережені.

Для початкової закритої бети Caddy пропускає тільки `ALLOWED_CLIENT_IPS`. За замовчуванням зовнішній доступ закритий. Це не заміна авторизації застосунку; це додаткове обмеження на час перевірок та оновлення залежностей.

## 1. Доступ та підготовка хоста

Переконатися, що VPS активний, є публічна IPv4, root/sudo-доступ і web-консоль відновлення від провайдера. Перевірити SSH fingerprint через панель/консоль; не вимикати StrictHostKeyChecking. Пароль root та приватні ключі не передавати в чат або Git.

У першому SSH-сеансі створити окремого користувача із sudo й додати свій публічний SSH-ключ. Перш ніж вимикати вхід root/паролем, перевірити вхід ключем і sudo в ДРУГОМУ сеансі; залишити перший відкритим. Не додавати звичайних користувачів до docker-group без усвідомлення, що це фактично root-доступ.

Для firewall дозволити реальний SSH-порт до ввімкнення правил, потім 80/tcp і 443/tcp. Не відкривати 3000, 4000, 5432 або Docker daemon TCP. Docker port publishing може обходити UFW, тому Compose навмисно не публікує внутрішні порти. Додатково можна застосувати firewall провайдера.

Зберегти репозиторій за `/opt/astro` (для приватного GitHub використовувати read-only deploy key або інший обмежений доступ). `/opt/astro` має бути недоступним для запису стороннім користувачам: systemd запускає скрипт із нього від root.

Після перегляду скрипта на ЧИСТОМУ VPS:

```bash
sudo bash /opt/astro/deploy/vps/bootstrap-ubuntu.sh
```

Скрипт ставить Docker із офіційного apt-репозиторію, Compose plugin та базові утиліти; за наявного Docker нічого не змінює. Не налаштовує SSH/firewall автоматично. Увімкнення та політику unattended security updates, вікно перезавантажень і моніторинг хоста налаштувати окремо. Не допускати неконтрольованого reboot під час консультацій.

## 2. Образи поза сервером

Файл `.github/workflows/publish-vps.yml` запускається лише вручну через GitHub Actions -> Publish VPS images -> Run workflow. Сам push не запускає ні тести, ні збірку, ні деплой.

Workflow збирає три Linux amd64 образи та публікує в GHCR:

```text
ghcr.io/highvoltage93/astro-api:sha-<повний commit SHA>
ghcr.io/highvoltage93/astro-web:sha-<повний commit SHA>
ghcr.io/highvoltage93/astro-backup:sha-<повний commit SHA>
```

Потрібні успішні ВСІ три jobs для того самого SHA. Web збирається з `NEXT_PUBLIC_API_URL=/api`, тому зміна домену не потребує перебудови браузерного коду. Тег прив'язаний до commit, а не `latest`; повторний build того самого SHA технічно може перезаписати tag, тому не перевидавати вже використані релізні теги. Для строгого відтворення можна надалі перейти на digest і зафіксувати базові образи/ефемериди.

Для приватних GHCR packages на VPS виконати `sudo docker login ghcr.io -u YOUR_GITHUB_LOGIN` та в інтерактивний запит передати токен із `read:packages`. Не давати серверу право публікувати образи. Облікові дані root Docker зберігаються на VPS, тому root-доступ потрібно захищати. Для публічних packages login не потрібен. GitHub Actions/registry мають власні квоти й можливу оплату.

## 3. Домен та секрети

Можна використати власний домен із A-записом на IPv4 VPS або тимчасовий `astro.<реальна-IP>.sslip.io`. Це тільки шаблон: вставити фактичну IP. Не додавати AAAA, якщо IPv6 не налаштовано. Для автоматичного HTTPS адреса повинна правильно резолвитися, а 80/443 бути доступними з інтернету. Ліміт видачі сертифікатів і залежність від стороннього DNS треба врахувати для тимчасового домену.

На VPS:

```bash
cd /opt/astro/deploy/vps
sudo cp .env.example .env
sudo cp .env.backup.example .env.backup
sudo chmod 600 .env .env.backup
sudoedit .env
sudoedit .env.backup
```

Для кожного з трьох паролів БД і JWT створити окреме значення `openssl rand -hex 32`. Саме hex-паролі не потребують URL-escaping. `SITE_HOST` — bare hostname, без `https://`, шляху та порту. `ALLOWED_CLIENT_IPS` — публічні IP тестувальників через пробіл, не адреса VPS. Не вказувати `0.0.0.0/0 ::/0` до завершення release-перевірок.

`IMAGE_TAG` у `.env` задає SHA релізу для звичайних compose-команд. `deploy.sh` отримує конкретний tag аргументом; останній успішний tag записується у `.deployed-tag`. Задача бекапів використовує саме `.deployed-tag`. Після успішного релізу погодити `IMAGE_TAG` у `.env` з ним, щоб ручні compose-команди не запустили старі образи.

При першій ініціалізації створюються `astro_owner` (міграції/адміністрування), `astro_app` (прикладні SELECT/INSERT/UPDATE/DELETE, без DDL) та `astro_backup` (читання). Runtime API не отримує пароль owner; після міграцій у runtime-role забирається доступ до `_prisma_migrations`. Пароль owner у PostgreSQL container залишається адміністративним секретом.

**Зміна .env не змінює паролі вже створених ролей.** Ротація потребує ALTER ROLE через адміністратора і погодженого оновлення конфігурації. Ніколи не видаляти volume, щоб «застосувати новий пароль».

## 4. Бекапи до перших клієнтських даних

У `.env.backup` налаштувати приватний S3 bucket іншого провайдера, обмежені credentials, age public recipient і URL незалежного dead-man monitor. Публічний ключ не розшифровує дані; приватний age key зберігати в менеджері паролів та окремій захищеній копії, не на VPS.

Схема шифрування, обмеження доступів bucket, retention (14 днів daily / 100 днів monthly), повідомлення та ручна перевірка відновлення описані у [розділах 4–5 інструкції бекапів](DEPLOY_RAILWAY_UK.md#4-незалежні-резервні-копії). Відмінність: замість Railway cron використовується systemd на VPS; Neon PITR у цьому варіанті НЕМАЄ. VPS workflow збирає backup із PostgreSQL client **16**, відповідно до сервера; для відновлення цих копій теж використовувати client 16, не 18 із попереднього прикладу для Railway. Для майбутнього major-upgrade узгоджено змінити сервер, backup client та процедуру відновлення.

`sslmode=disable` дозволений тільки для hostname `postgres` у приватній мережі з явним `ALLOW_PRIVATE_DATABASE=true`. Зовнішні підключення до БД, як і раніше, вимагають TLS. Контейнер backup має окремий outbound-доступ до сховища. Ця модель довіряє адміністраторам та ядру хоста, не шифрує трафік всередині одного VPS.

Ціль втрати даних при аварії — до доби за останнього успішного daily dump, не PITR. Якщо це неприйнятно, окремо потрібне архівування WAL (наприклад pgBackRest) або керована БД. Бекап VPS від провайдера — додатковий шар, не заміна незалежного дампа.

## 5. Перший запуск

Після публікації образів і заповнення конфігурації:

```bash
sudo bash /opt/astro/deploy/vps/deploy.sh sha-REPLACE_WITH_FULL_40_CHARACTER_SHA
```

Скрипт встановлює lock від одночасного деплою/бекапу, завантажує образи, запускає PostgreSQL, визначає наявність таблиць, зупиняє web/API/Caddy на час релізу, для наявної БД вимагає успішний off-site backup, виконує міграції та запускає сервіси з очікуванням readiness. Для порожньої нової БД попередній дамп пропускається. Це **деплой із коротким простоєм**, не zero-downtime.

У разі помилки скрипт не відновлює БД і не запускає автоматичний rollback; сервіси можуть залишитися зупиненими до втручання. Не обходити невдалий бекап для наявної production-БД. Налаштування healthcheck є частиною майбутнього запуску; зараз вони не виконувалися.

Після запуску з дозволеної IP перевірити HTTPS, реєстрацію/логін, натальну карту, збереження, повторне відкриття й консультацію. Користувач admin автоматично не створюється. Не переносити тестовий пароль `admin` у production.

## 6. Щоденний таймер

```bash
sudo install -m 644 /opt/astro/deploy/vps/systemd/astro-backup.service /etc/systemd/system/
sudo install -m 644 /opt/astro/deploy/vps/systemd/astro-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now astro-backup.timer
sudo systemctl start astro-backup.service
```

Це реальний запуск бекапу, який треба виконати на VPS після конфігурації. Таймер: 02:15 UTC плюс до 5 хвилин випадкової затримки; пропущений під час reboot запуск надолужується. Зовнішній monitor очікує успіх щодоби з grace period 2 години та повідомляє і про помилку, і про повну відсутність запуску. Перед відкриттям реєстрації зробити ізольоване відновлення копії.

## 7. Щоденна робота та наступні релізи

```bash
cd /opt/astro/deploy/vps
sudo docker compose --env-file .env -f compose.yaml ps
sudo docker compose --env-file .env -f compose.yaml logs --tail=100 api
sudo journalctl -u astro-backup.service --since today
sudo systemctl list-timers astro-backup.timer
df -h
sudo docker system df
```

Для оновлення: опублікувати нові образи workflow, синхронізувати код репозиторію на VPS з відповідним commit (без втрати `.env`), переглянути міграції й виконати `deploy.sh` з новим SHA. Робити це у вікно обслуговування. Зберігати попередній образ для відкату коду; `.previous-tag` — підказка, не автоматичний rollback. Старий код можна повернути тільки якщо він сумісний із поточною схемою БД.

Не запускати `docker compose down -v`, `docker volume prune`, `prisma migrate reset` або `db push --accept-data-loss` на production. Контейнери й образи можна відтворити, volume БД — ні без копії. Очищення старих образів робити вручну після перевірки rollback-tag, не автоматично через загальний prune.

Логи Docker обмежені 3 файлами по 10 MB на контейнер. Ліміти RAM: API 1536 MB, web 640 MB, PostgreSQL 640 MB, Caddy 128 MB, backup 384 MB. Це початкові налаштування, не гарантія місткості; потрібні вимірювання. Під час pre-deploy web/API зупинені, щоб міграції/бекап не конкурували з ними за пам'ять. Swap може допомогти пережити піки, але не замінює RAM.

Додати зовнішній uptime-monitor та сповіщення про диск (наприклад 75% і 85%), RAM, помилки контейнерів, невдалі бекапи. Для доступу monitor при IP allowlist дозволити його адреси окремо. Healthcheck позначає контейнер unhealthy, але сам по собі не гарантує його restart.

## 8. Існуючі дані та restore

Не переносити фізичний каталог PostgreSQL між випадковими версіями. Використовувати дамп і відновлення у чисту ціль. На час фінального перенесення призупинити запис на джерелі. Baseline `0_init` позначати застосованим лише після перевірки фактичної схеми, як описано в попередній інструкції. Для імпортованих таблиць окремо видати `astro_app` права на таблиці й sequences: default privileges стосуються тільки майбутніх об'єктів. Не відновлювати старі власники/ACL поверх нової моделі ролей.

Щомісяця розшифровувати копію й відновлювати в окрему порожню тестову БД. Перевірити користувачів, карти, консультації та історію. Не передавати `--clean` або production URL для навчальної перевірки. Зафіксувати час відновлення. Самі SHA-256 та успішний upload не доводять, що БД можна відновити.

## Перед публічним доступом

Залишити IP allowlist, доки не пройдено production build/runtime перевірки, контроль точності, restore drill та перевірку прав доступу. Окремими роботами лишаються оновлення Next.js 14.2.7/інших застарілих залежностей, захист логіну й дорогих розрахунків від зловживань, ліцензія Swiss Ephemeris. Не відкривати доступ реальним клієнтам лише тому, що контейнери запустилися.
