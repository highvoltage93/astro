# Консультації: перший етап v1

## Сценарій роботи

1. Відкрити власну збережену натальну карту у робочій зоні.
2. Над правою панеллю вибрати «Консультація», потім «Створити консультацію».
3. Заповнити назву, розділи й окремі приватні нотатки. Розділи можна додавати, перейменовувати, переставляти та видаляти з підтвердженням.
4. Текст автоматично зберігається через 1.2 секунди після паузи у введенні. Є також кнопка ручного збереження та видимий стан запиту.
5. У вкладці «Перегляд» відображається лише клієнтський текст. Приватні нотатки туди не включаються.
6. Позначити документ «Готово». Подальше редагування клієнтського тексту повертає статус «Чернетка». Статус не публікує документ і не відкриває доступ клієнту.

Редактор у правій панелі має незалежний скрол на широкому екрані. Перемикання між таблицями та консультацією приховує, але не видаляє відкритий редактор; перемикання методів прогнозу також його не закриває. На мобільному використовується вертикальне компонування. Кнопка розгортання відкриває окрему вкладку з **серверною** версією документа; незбережені зміни не передаються між вкладками.

На дешборді є список «Мої консультації». Посилання `/consultations?id=...` відкриває повносторінковий редактор, `/consultations` показує список. Обидва сценарії потребують авторизації. Список упорядковано за датою створення, нові спочатку; дата останньої зміни вказана окремо.

Редактор розділів використовує Tiptap 3.31.3: жирний, курсив, підкреслення, закреслення, абзаци, два рівні заголовків, марковані/нумеровані списки та цитати. Кнопки скасування й повтору працюють у межах окремого розділу. Перемикання на приватні нотатки чи перегляд не знищує редактори та їхню поточну історію. Після закриття документа/refresh ця історія не відновлюється; додавання, видалення та перестановка розділів не входять до undo/redo текстового редактора.

Вставлення з Word/браузера обробляється схемою Tiptap: підтримувані абзаци й виділення можуть зберігатися, але це не точний імпорт Word. Зображення, посилання, таблиці, довільні стилі та HTML-атрибути не входять до дозволеного формату. Таблиці й зміна ширини панелей заплановані окремо.

## Клієнтський документ і PDF

Кнопка «Друк / PDF» у редакторі активна після підтвердженого збереження, без локальної чернетки, запиту в польоті чи конфлікту. Вона відкриває `/consultations/print?id=...&revision=...` в окремій вкладці. Це захищена сторінка для астролога, не публічне посилання для клієнта.

Друк використовує окремий API `GET /consultations/:id/client-document`. Сервер перевіряє власника й очікувану редакцію, а потім явно формує відповідь: назва, статус, редакція, час збереження, розділи та обмежені метадані джерела. Приватні нотатки навіть не вибираються з БД; повний знімок карти не передається клієнтській сторінці. Якщо редакція змінилася, повертається `409` з можливістю явно відкрити актуальну, а не мовчки підмінити текст.

У попередньому перегляді можна вибрати розділи, показувати/приховувати окремий рядок імені та блок даних народження/розрахунку. Дані народження вимкнені за замовчуванням. Ці перемикачі не видаляють імена чи дати, які астролог сам написав у назві або тексті; перед передаванням документа потрібен перегляд. Налаштування експорту діють лише в цій вкладці й не змінюють збережений документ. Потрібен щонайменше один розділ, карта або таблиця; можна друкувати тільки вибрані додатки без текстових розділів.

Документ має друковане компонування A4, поля 18/16 мм, читабельний чорно-білий текст, списки й заголовки. Довгі розділи можуть переходити на наступну сторінку; заголовки мають залишатися разом із наступним текстом. Чернетка друкується з позначкою «Чернетка». Приватні нотатки в DOM друкованого документа відсутні.

«Друк / PDF» викликає системний діалог браузера; для PDF користувач обирає «Зберегти як PDF». Окремий серверний PDF-файл не генерується і на сервер не завантажується. Колонтитули браузера, фактична пагінація й підтримка PDF залежать від браузера.

### Карти та вибіркові таблиці

У блоці «Карти та таблиці» є незалежні перемикачі: натальна карта, натальні положення, натальні аспекти, карта соляру, положення соляру, аспекти всередині соляру та важливі дати. Усі додатки за замовчуванням вимкнені, тому звичайний друк тексту не змінюється.

Натальні дані беруться з незмінного знімка консультації. Для соляру й дат потрібно вибрати власний збережений прогноз у розгорнутому архіві: є пошук за назвою та пагінація. Прогноз не перераховується. Якщо в ньому немає соляру, відповідні перемикачі недоступні, але можна використати наявні дати. Новий вибір прогнозу скидає вибір дат і підтвердження сумісності, щоб попередній набір не потрапив у PDF під новою назвою.

Сумісність натальних знімків порівнюється за UTC-моментом, відомістю часу народження, координатами, спроєктованими налаштуваннями, положеннями, домами й аспектами. Відмінність чи відсутність достатніх даних вимагає окремого підтвердження користувача. Це консервативне порівняння структур, не встановлення особи: однакові астрологічні знімки не доводять, що ім'я клієнта правильне. Перед друком видно назву прогнозу й особу з архіву.

Карти використовують той самий SVG `ChartWheel`, що й робоча зона, без повторного обчислення положень. Друкований режим прибирає інтерактивне виділення та нижню панель, має незалежні ID стрілок для кожної карти й показує всі наявні аспекти між десятьма основними планетами без екранного обмеження 24. Куспіди й додаткові точки не включаються в аспекти; доми, кути та додаткові точки залишаються на колі. Соляр друкується як окреме колесо карти повернення, не як подвійне накладання на натальну карту. Ретроградність позначається `R` за збереженою швидкістю `< -0.0001`.

Таблиці:

- Положення: спочатку Сонце–Плутон, потім додаткові точки й кути; знак, градус до кутової секунди вниз (не вище 29°59′59″), дім та рух. Для кутів рух не показується. Стаціонарність: `abs(speed) < 0.0001`; ретроградність: `speed < -0.0001`; інакше директний рух. Відсутні значення не обчислюються заново.
- Аспекти: лише між десятьма основними планетами. `exactAngle` явно називається кутом аспекту, а не фактичною відстанню; орбіс із знімка показується до чотирьох знаків. Таблиця соляру містить внутрішні аспекти карти повернення, не аспекти соляр–натал.
- Важливі дати: вибрані користувачем рядки `timelineEvents`, відсортовані за моментом. Є пошук, показ порціями по 50, вибір показаних та очищення. Якщо момент соляру відсутній у календарі, додається рядок зі збереженим `solarReturn.exactAt`; однаковий момент з іншим UTC-offset не дублюється. Прогресії та сонячна дуга позначені як розрахункові дати. Усі моменти подаються в UTC, незалежно від часового поясу браузера; нових дат не обчислюємо.

Для карт і таблиць виводяться система домів та зодіак, збережені попередження розрахунку; для соляру — момент повернення, для прогнозних додатків — час знімка. При невідомому часі народження є відповідна примітка. Вимкнення блоку даних народження не приховує дату соляру або явно вибрані прогнозні дати.

Порядок поки фіксований: текстові розділи, натальна карта/таблиці, соляр/таблиці, дати. Перестановку блоків, ім'я/контакти астролога та оформлення обкладинки в цьому кроці не додано. Налаштування додатків не зберігаються в консультації й скидаються після закриття/оновлення сторінки друку.

Дані завантажуються через окремі маршрути:

- `GET /consultations/:id/print-assets?revision=...&forecastId=...`: обов'язкова перевірка власника консультації та її редакції; прогноз також повинен належати цьому власнику й бути типу `forecast`. Чужий/видалений прогноз дає `404`, зміна редакції — `409`. Відповідь містить лише дозволені поля карти, соляру, дат і попереджень. Приватні нотатки консультації, нотатки архіву, внутрішні трактування та повні параметри народження не передаються.
- `GET /consultations/:id/print-forecasts?query=...&cursor=...`: тільки ID, назва й дата створення власних прогнозів; список також потребує доступу до консультації. Обидва маршрути повертають `Cache-Control: private, no-store`.

Якщо знімок не підтримується, можна вимкнути додатки й друкувати тільки текст. Поки вибрані додатки не завантажені, не підтверджено прогноз або для таблиці дат не вибрано рядків, кнопка друку заблокована. Для системного Ctrl/Cmd+P в такому стані друкується попередження замість неповного документа. Перед викликом друку очікуємо завантаження шрифтів; зміна вибору під час очікування скасовує цей виклик.

Друковане колесо має обмеження висоти 170 мм і не повинно розриватися між сторінками; таблиці не мають внутрішнього скролу, заголовки повторюються на наступних сторінках, рядки позначені нерозривними. Фактична підтримка цих CSS-правил залежить від браузера. Додано контрольні сценарії приватної проєкції (включно з вкладеними сторонніми полями), власника, редакції, сумісності знімків, точності відображення, фільтрації аспектів і сортування/дедуплікації дат. Тести, typecheck, друк і візуальні перевірки не запускалися за поточною домовленістю. Потрібна ручна перевірка A4, двох карт, довгих таблиць, кирилиці/символів, мобільного перегляду та друку без кольорового фону.

Нових npm-залежностей і міграцій БД немає. API потрібно оновити/перезапустити (`docker compose restart api`), фронтенд використовує чинний hot reload.

## Незмінне джерело

У вкладці «Дані карти» можна знайти та вибрати положення точок, управління домами й аспекти, а потім вставити їх у кінець наявного розділу або створити новий. Джерело: лише `record.source.chart`, не поточні налаштування робочої зони. Вибір зберігається між категоріями та очищується після успішного вставлення.

Положення впорядковані від Сонця до Плутона, потім додаткові точки й кути. Знак, градус, дім, швидкість і `planetRulerships` беруться зі знімка. Градус подається до цілої кутової секунди вниз, не переходячи за 29°59′59″. Рух: стаціонарний при `abs(speed) < 0.0001`, ретроградний при `speed < -0.0001`, інакше директний; для кутів не показується. Управління не перераховується.

Аспекти вставляються лише між десятьма основними планетами, без куспідів, кутів та додаткових точок. `exactAngle` позначений як **кут аспекту**, не фактична відстань між планетами; орбіс береться зі знімка до чотирьох знаків після коми. Нові аспекти не обчислюються.

Перед вставленими рядками додається час знімка. Це звичайний редагований текст, не живе посилання: ручні зміни астролога не звіряються з картою. Автоматичних трактувань немає. Вставлений текст потрапляє у клієнтський документ і PDF разом із вибраним розділом. Приватні нотатки не додаються.

Вставлення повертає статус «Чернетка» та використовує чинне автозбереження. При перевищенні лімітів чи видаленому розділі призначення попередній текст залишається без змін. Додані, але не запущені, сценарії незмінності джерела, фільтрації аспектів, граничних градусів та доповнення старого тексту.

Створення дозволене тільки для власної збереженої карти. Сервер сам читає останній збережений натальний розрахунок та записує його копію в `sourceSnapshotJson` разом з ім'ям, місцем, датою/часом народження, часовим поясом і часом розрахунку. Клієнт не передає результат карти.

`sourceProfileId` і `sourceCalculationId` є довідковими ідентифікаторами, не зовнішніми ключами. Видалення вихідної карти не видаляє консультацію чи її знімок. Оновлення орбісів, управителів або часу народження не переписує джерело документа. Після зміни параметрів потрібно зберегти нову карту й створити для неї окрему консультацію. Автоматичного порівняння старого й нового джерел на цьому етапі немає.

Астрологічне ядро та формули у цьому кроці не змінюються. Консультація не виконує повторного розрахунку.

## Прогнозні події в консультації

Вкладка «Прогнози» відкриває власний архів: пошук за назвою, фільтр «Соляр, лунар і прогностика» / «Транзити», сторінки по 10 записів. Після вибору видно назву, особу та час знімка. Архів не обмежений поточною натальною картою: відповідність особи та вихідних даних астролог перевіряє перед вставленням. Синастрія в цьому кроці не включена.

Джерела даних без перерахунку:

- Для транзитного запису: `transitToNatalAspects`, дата зрізу `input.parameters.transitDateTime`, збережені `exactAt`, `activeFrom`, `activeUntil`. Відсутня точна дата явно позначається, не замінюється датою зрізу.
- Для соляру/лунару: `solarReturn` / `lunarReturn`, момент повернення, наступне повернення (якщо є), положення точок у карті повернення та `returnToNatalAspects`. Доми й управління положень стосуються карти повернення; аспекти показуються до натальних точок.
- Для календаря прогнозу: `timelineEvents`, включно з транзитами, вторинними прогресіями й дирекціями сонячної дуги. Дати прогресій/дирекцій називаються розрахунковими. Повернення не дублюється з календаря, якщо вже є окремий результат соляру/лунару.

Дати переводяться в UTC через `Date.toISOString()`, зі збереженням моменту та мілісекунд. Локальний пояс браузера не впливає на вставлені дати. Пояс народження показується окремо й не використовується як пояс місця повернення. Нові корені точних аспектів, орбіси чи координати не обчислюються. Кут аспекту не є фактичною кутовою відстанню; орбіс показується до чотирьох десяткових знаків зі знімка.

Можна знайти події за текстом, вибрати кілька та додати в кінець наявного або нового розділу «Прогнозні події». Заголовок вставки містить назву прогнозу, особу, час розрахунку, UTC, пояс народження, систему домів, зодіак і координати повернення для прогностичного запису. Увесь текст редагований і потрапляє в PDF; приховування окремого блоку імені у друці не прибирає ім'я з цього тексту.

Кожен розділ може містити `forecastSources`: `{ forecastId, eventId, generatedAt, timezone: "UTC" }`, до 500 записів. Ідентифікатор події стабільний у межах незмінного архівного запису. Повтор перевіряється за парою `(forecastId, eventId)` у всіх розділах; уже додані події позначаються й блокуються. Це зберігається в БД та локальній чернетці разом із текстом, переживає refresh і редагування. Джерела є довідковими метаданими, не серверною атестацією правильності тексту. У відповіді для клієнтського друку ці службові метадані відсутні.

Видалення цілого розділу видаляє його позначки імпорту й дозволяє вставити події знову, якщо їх немає в інших розділах. Ручне видалення рядка не знімає позначку: автоматичного зіставлення відредагованого тексту немає. Однакові події з різних архівних записів не об'єднуються. Видалення прогнозу з архіву не видаляє вже вставлений текст. Повного знімка прогнозу в консультації немає, зберігаються вибрані текстові дані й посилання на джерело.

Нових залежностей і міграцій БД немає. Для застосування змін спільної JSON-схеми перезапустити API перед вставленням подій: `docker compose restart api`. Фронтенд оновлюється через наявний hot reload.

Додані, але не запущені контрольні сценарії: однаковий локальний час з різними UTC-offset на переході DST; відсутня точна дата; незмінність джерела; збереження попереднього тексту; дублікати після JSON-відновлення та редагування; новий/видалений розділ; відсутність подвійного повернення з календаря. Ручні сценарії: повільне завантаження й перемикання архіву; помилка мережі та повтор; автозбереження/refresh; вставлення у готовий документ повертає його в чернетку; мобільна ширина й клієнтський PDF. У цьому кроці тести, typecheck і сервери не запускалися.

## Особиста бібліотека шаблонів

У редакторі консультації є вкладка «Бібліотека». Це приватні тексти користувача, спільні для його консультацій, а не автоматичні астрологічні трактування. Бібліотека не виконує розрахунків і не підставляє імена, планети чи дати.

Сценарій:

1. «Новий шаблон» відкриває порожню чернетку. «З розділу консультації» копіює лише назву й текст вибраного розділу. Приватні нотатки, знімок карти та службові посилання прогнозів не копіюються.
2. Назвати шаблон, вибрати категорію (загальне, натальна карта, транзити, соляр, лунар, синастрія) та відредагувати текст у тому самому форматованому редакторі.
3. Натиснути «Зберегти шаблон». Шаблони зберігаються вручну, окремо від автозбереження консультації. Список шукає за назвою без урахування регістру, фільтрує категорію й показує по 10 записів, нові за датою створення першими; на рядку видно дату останньої зміни.
4. Вибрати збережений шаблон і розділ призначення. «Вставити шаблон» додає копію форматованого тексту в кінець розділу або створює новий із назвою шаблону. Вставлення недоступне, поки правки шаблону не збережені або збереження не підтверджено.
5. За потреби «Створити копію» створює нову локальну чернетку з іншим ID; її також потрібно окремо зберегти. Видалення з підтвердженням доступне для збереженої версії без незбережених правок.

Копіювання розділу переносить буквальний текст, включно з іменами чи іншими персональними даними, якщо вони вже вписані в цей розділ. Автоматичної анонімізації немає: перед повторним використанням прибрати індивідуальні дані вручну. Приватні нотатки як окреме поле ніколи не стають джерелом шаблону.

Вставлення є незалежною копією: подальше редагування або видалення шаблону не змінює консультацій. Воно переводить консультацію в «Чернетку» й використовує її чинне автозбереження. При переповненні документа чи відсутньому розділі нічого не вставляється. Наявні посилання прогнозів у розділі зберігаються. Повторне вставлення одного текстового шаблону дозволене: на відміну від прогнозної події, це повторно використовуваний текст.

Захист даних:

- Таблиця `consultation_templates`: UUID шаблону, власник, назва, категорія, `bodyJson`, `revision`, `lastMutationId`, дати створення/оновлення. Усі запити вимагають авторизації; власник визначається лише з токена. Список не містить тіл шаблонів. Відповіді мають `Cache-Control: private, no-store`.
- Створення з клієнтським UUID і порожнім `upsert.update` дозволяє повторити запит після втраченої відповіді без створення дубля. UUID іншого власника не розкриває його текст.
- Оновлення атомарно перевіряє власника, ID та `revision`. Інша редакція повертає `409`; текст у редакторі залишається. Для повтора після мережевої помилки зберігаються ті самі параметри й `mutationId`, а редагування тимчасово заблоковане. Можна повторити запит, завантажити актуальну версію з підтвердженням або створити окрему копію свого тексту.
- Видалення також вимагає очікуваної редакції, тому не видалить новіші правки іншої вкладки. Повторне видалення вже відсутнього запису безпечне. Видаляється лише шаблон, не консультації.
- Незбережений шаблон і незавершений запит мають одну локальну чернетку на користувача в `sessionStorage` поточної вкладки. Вона відновлюється при відкритті бібліотеки; перемикання вкладок редактора її не знищує. Перехід на інший шаблон питає підтвердження відкидання правок. При закритті/refresh є попередження. Це не постійна резервна копія: після закриття вкладки локальні дані можуть бути втрачені.

Ліміти шаблону: назва 1–120 символів після обрізання пробілів, тіло до 20 000 текстових символів, дозволена схема rich-text без зображень/посилань/довільного HTML, JSON чернетки до 100 000 символів. Для нового розділу консультації діють її окремі ліміти.

API:

| Метод | Маршрут | Призначення |
| --- | --- | --- |
| GET | `/consultation-templates` | Власні шаблони; `query`, `category`, `cursor`, `limit` |
| GET | `/consultation-templates/:id` | Власний шаблон з текстом |
| POST | `/consultation-templates` | `{ id, draft: { title, category, body } }` |
| PUT | `/consultation-templates/:id` | `{ revision, mutationId, draft }` |
| DELETE | `/consultation-templates/:id?revision=...` | Видалення очікуваної редакції |

Для Docker development потрібен `docker compose restart api`: чинний startup генерує Prisma Client та додає нову таблицю через `db:push`. Нових npm-залежностей немає. Існуючі таблиці й розрахунки не перезаписуються. Для production потрібна окрема перевірена міграція; не обходити попередження через скидання БД або `--accept-data-loss`.

Додано `corepack pnpm --filter @astroprocessor/api test:templates`: сценарії авторизації, приватності списку, чужих ID/cursor, ідемпотентного створення, конфліктів оновлення/видалення, валідації та незалежного вставлення тексту зі збереженням джерел прогнозів. Ці тести, typecheck та браузерні перевірки не запускалися. Ручні сценарії: створення з розділу, відновлення чернетки після refresh, мережевий повтор, дві вкладки, вставлення rich-text, мобільний вигляд, видалення шаблону без зміни консультації.

У цьому кроці також виправлено формат `forecastSources.forecastId`: архів використовує CUID, тому поле приймає непорожній рядок до 120 символів, а не лише UUID. Контрольний сценарій вставлення прогнозу використовує CUID.

## Історія версій консультації

Вкладка «Історія» показує збереження за номером редакції від нових до старих, по 10 на сторінку. У списку видно номер, час збереження, назву, статус та позначку поточної серверної версії. Відкриття рядка показує клієнтський текст тільки для читання; приватні нотатки доступні окремо у згорнутому блоці. Список не передає текстів або нотаток. Історія доступна лише власнику; публічного доступу до неї немає.

Зберігання:

- Нова таблиця `consultation_revisions` має складений ключ `(consultationId, revision)`, зв'язок із консультацією, назву, статус, `contentJson`, приватні нотатки та `savedAt`. Час береться з `Consultation.updatedAt` відповідної редакції, не з моменту перегляду історії.
- Створення нової консультації та запис її першої версії виконуються в одній транзакції. Кожне наступне успішне збереження записує нову редакцію. Зміни статусу чи лише нотаток також потрапляють в історію.
- Оновлення спочатку читає попередню версію, потім атомарно змінює документ за `(id, ownerUserId, revision)`. У тій самій транзакції зберігає попередню й нову версії. Наявний історичний запис ніколи не перезаписується (`upsert.update = {}`). Помилка запису історії відкочує всю транзакцію, включно з текстом консультації.
- Повтор підтвердженого запиту з тим самим `mutationId` використовує чинний механізм ідемпотентності та не створює нової редакції. Запит іншої вкладки із застарілим номером повертає конфлікт.
- Для консультацій, створених до появи історії, початкова історична точка записується під час їхнього наступного успішного збереження разом із новою версією. Саме відкриття історії нічого не записує. Редакції, які вже були перезаписані до оновлення, відсутні та не відновлюються.
- Незмінний натальний знімок не дублюється у кожному збереженні й не перераховується. Дані бібліотеки шаблонів не мають своєї історії в цій таблиці. Текст, форматування й `forecastSources` зберігаються разом у версії консультації.

Відновлення:

1. Спочатку зберегти поточні зміни та вирішити мережеві помилки/конфлікти. Кнопка відновлення заблокована за наявності локальної чернетки, незавершеного запиту або іншої поточної редакції на сервері.
2. Відкрити попередню версію. За замовчуванням відновлюються її назва й клієнтський текст; поточні приватні нотатки залишаються. Для їх заміни потрібна окрема позначка «Також відновити приватні нотатки».
3. Підтвердити «Відновити як нову редакцію». Історична копія не змінюється; її текст стає новою чернеткою зі статусом `DRAFT` і відразу надсилається через звичайний механізм збереження. Поточна версія залишається в історії. Нова редакція створюється навіть якщо вибраний текст збігається з поточним.
4. При помилці відновлений текст залишається локально; діють повтор збереження, відновлення після refresh та захист від паралельних змін. Якщо інша вкладка встигла змінити документ після відкриття історії, перевірка `revision` не дозволить мовчки перезаписати її зміни.

Перегляд історії сам по собі не змінює дані для друку. Друкується поточна підтверджена редакція, а не відкритий історичний рядок. Приватні нотатки не потрапляють у клієнтський документ.

Нові маршрути: `GET /consultations/:id/history?before=<revision>&limit=10` та `GET /consultations/:id/history/:revision`. Обидва потребують авторизації й повертають `Cache-Control: private, no-store`. На детальному запиті власник перевіряється через зв'язок версії з консультацією. Чужі або відсутні записи дають `404`, непідтримуваний формат тексту дає `422`.

На цьому етапі зберігається кожне підтверджене збереження без автоматичного проріджування або строку видалення; це збільшує обсяг БД, особливо при частому автозбереженні великих документів. Історія не замінює резервне копіювання БД. Підсвічування окремих змінених слів/рядків, підписані контрольні версії та керована політика зберігання поки не реалізовані.

### Порівняння перед відновленням

Після вибору історичної версії доступні режими «Текст версії» та «Порівняння». Напрям порівняння: **обрана історична версія → остання підтверджена редактором збережена версія**. Обидва номери явно підписані. Незбережений текст у поточній вкладці не підміняє праву сторону. Після успішного збереження основа порівняння оновлюється. Якщо історія повідомляє про іншу версію на сервері, показується попередження; автоматичного перезапису або підміни локального редактора немає.

Показуються зміни назви й статусу документа, кількість доданих/видалених/змінених/незмінених розділів. За замовчуванням видно лише змінені розділи; кожен можна розгорнути й побачити обидва варіанти з вихідним форматуванням. На вузьких екранах тексти йдуть один під одним. Це порівняння **на рівні розділів**, без автоматичного злиття та без позначення окремих змінених слів.

Правила:

- Розділи зіставляються за стабільним UUID, не за назвою чи номером. Повторення назв не поєднує різні розділи. Видалений і заново створений розділ із новим UUID відображається як видалення та додавання, навіть якщо текст той самий.
- Для спільного UUID окремо позначаються назва, текст, зміна лише форматування/структури, джерела прогнозів та порядок. Перестановки визначаються за відносним порядком спільних розділів: саме додавання або видалення сусіднього розділу не позначає всі наступні як переміщені.
- Для порівняння тіла plain text тимчасово перетворюється у структуру абзаців, потім обидві структури перевіряються спільною схемою. Порядок JSON-ключів, порядок еквівалентних виділень і явно записані стандартні атрибути нумерованого списку не вважаються зміною. Оновлення формату з `version: 1` на `version: 2` саме по собі не є зміною тексту.
- Текст порівнюється зі збереженням пробілів і меж абзаців; зміна структури при однаковому тексті позначається як «Форматування / структура». Підсвічування конкретних слів немає.
- Джерела прогнозів порівнюються за значеннями полів без урахування порядку масиву. Позначка зміни джерела не означає перерахунок астрологічних даних.
- Приватні нотатки порівнюються окремо в згорнутому блоці. Вони не додаються до клієнтського перегляду або PDF. Їх відновлення, як і раніше, вимагає окремої позначки.

Порівняння виконується локально над уже отриманими даними: нових API, таблиць, залежностей чи змін у збереженні немає. Усі вихідні документи залишаються незмінними. До `test:consultations` додані сценарії plain/rich еквівалентності, форматування, тексту, додавання/видалення, перестановок, однакових назв, приватних нотаток, джерел і стандартних атрибутів. Тести, typecheck та візуальні перевірки в цьому кроці не запускалися.

Для Docker development: `docker compose restart api` генерує Prisma Client і додає таблицю через чинний startup. Дані наявних консультацій не скидаються. Для production потрібна перевірена міграція без `--accept-data-loss`.

До `test:consultations` додано сценарії транзакційного запису обох версій, відмови історичного запису до коміту транзакції (тест із підставною БД), приватності списку, пагінації, перевірки власника, читання старого формату та незалежного відновлення з вибором приватних нотаток. Тести, typecheck, браузерні сценарії та реальна транзакція PostgreSQL у цьому кроці не запускалися. Ручні сценарії: нова/стара консультація, повторне відкриття тієї самої версії, дві вкладки, мережевий збій під час відновлення, повернення нотаток за позначкою, збереження історії після refresh, мобільний вигляд.

## Автозбереження та відновлення

- Запити збереження виконуються послідовно. Текст, введений під час запиту, залишається в редакторі й зберігається наступним запитом.
- Кожна зміна вимагає очікуваної `revision`. Оновлення атомарно перевіряє `(id, ownerUserId, revision)` і збільшує редакцію на одиницю.
- При одночасному редагуванні інша вкладка отримує `409`. Автозбереження зупиняється, її локальний текст не замінюється серверним. Можна завантажити приватну резервну копію, а потім явно завантажити серверну версію з підтвердженням відкидання чернетки. Автоматичного злиття немає.
- `mutationId` дозволяє повторити останній запит після втраченої відповіді. При мережевій помилці повтор надсилає той самий вміст, редакцію та ID; нові правки надсилаються після його підтвердження.
- Чернетка і незавершений запит дублюються в `sessionStorage`, ключ містить ID користувача й документа. Після refresh можна відновити або відкинути чернетку. Застаріла редакція не перезаписує сервер без перевірки.
- Локальна копія належить вкладці, не є постійним резервним сховищем і може зникнути після її закриття. При недоступності сховища показується попередження. При незбереженому тексті додається браузерне попередження перед закриттям/перезавантаженням.
- Кнопка приватної резервної копії завантажує JSON із текстом **та приватними нотатками**. Це не клієнтський експорт і не PDF. Імпорт JSON у редактор ще не реалізований.

Номер `revision` захищає від конфліктів і є ключем збереженої історичної версії. Старі редакції до впровадження історії відсутні; правила початкової точки описані вище.

## API та обмеження

| Метод | Маршрут | Призначення |
| --- | --- | --- |
| GET | `/consultations` | Власні документи, необов'язкові `sourceProfileId`, `cursor`, `limit` (1–50) |
| GET | `/consultations/:id` | Власний документ, нотатки та знімок джерела |
| GET | `/consultations/:id/client-document` | Клієнтський текст без приватних нотаток, необов'язкова очікувана `revision` |
| GET | `/consultations/:id/history` | Список збережених версій без тексту й нотаток |
| GET | `/consultations/:id/history/:revision` | Повна історична редакція для власника |
| POST | `/consultations` | Створення з UUID клієнта та ID власної карти; повтор із тим самим ID не створює дублікат |
| PUT | `/consultations/:id` | Збереження тексту, статусу й нотаток з `revision` та `mutationId` |

Усі маршрути вимагають авторизації та повертають `Cache-Control: private, no-store`. Публічного або клієнтського endpoint немає. Список не містить тексту, приватних нотаток чи результатів карти. Власник визначається з токена, не з тіла запиту.

Структура документа: `{ version, sections: [{ id, title, body }] }`.

- `version: 1`: `body` є звичайним текстом; старі документи та локальні чернетки продовжують читатися і зберігатися.
- `version: 2`: `body` може бути структурованим JSON-документом Tiptap або ще не редагованим старим текстом. Версія змінюється при першій зміні в rich-text редакторі. Конвертується лише відредагований розділ, не вся база й не весь документ. Саме відкриття документа не запускає міграцію чи збереження.
- Порожні рядки та буквальний текст на кшталт `<b>...</b>` старого документа не перетворюються на HTML під час відкриття.

Спільний пакет `@astroprocessor/consultation-format` задає схему для API, локального відновлення та редактора. Дозволені вузли: doc, paragraph, heading (2/3), text, hardBreak, blockquote, bulletList, orderedList, listItem; виділення: bold, italic, underline, strike. Невідомі вузли й атрибути відхиляються, а не мовчки стираються під час збереження. Невідомі версії документа не приймаються.

До 30 розділів, до 200 символів у заголовку, до 20 000 текстових символів у розділі, до 200 000 символів у JSON документа; назва консультації до 120 символів, приватні нотатки до 10 000. Для rich-text додатково обмежені глибина дерева (12) та кількість вузлів (5000 на розділ). Редактор відхиляє транзакції, що порушують ці межі, зі збереженням попереднього тексту та повідомленням. Сервер перевіряє ті самі межі незалежно від UI.

Клієнтський перегляд складається з дозволених React-елементів із екранованим текстом, без `dangerouslySetInnerHTML`. У нього передаються лише назва та розділи документа, не приватні нотатки. Історія undo/redo залишається локальним станом редактора і не входить до збереженого JSON.

## Оновлення та перевірки

Додана таблиця `consultations`, що належить користувачу. Для поточного Docker development-сценарію:

```bash
docker compose restart api
```

Для оновлення з версії без Tiptap потрібно перебудувати API/web та їхні анонімні томи залежностей:

```bash
docker compose up -d --build --force-recreate --renew-anon-volumes api web
```

Іменований том `postgres-data` ця команда не видаляє. Нове поле у БД для rich-text не потрібне: використовується попередній `contentJson`. Під час запуску генерується Prisma Client і застосовується схема. Не використовувати скидання БД або `--accept-data-loss` для обходу несподіваних попереджень. Для production потрібна окрема перевірена міграція.

Додані API-сценарії:

```bash
corepack pnpm --filter @astroprocessor/api test:consultations
corepack pnpm --filter @astroprocessor/consultation-format test
```

Вони покривають доступ, копію джерела, приватність списку, повтор створення, конфлікт редакцій і повтор втраченої відповіді; додані сценарії сумісності plain/rich-text, форматованого JSON, заборонених вузлів/атрибутів та меж вкладеності. Тести, typecheck, браузерні сценарії та сервер у цьому кроці не запускалися за домовленістю з користувачем.

Додаткові ручні сценарії: форматування та paste з Word; збереження/refresh без втрати списків і виділень; undo/redo після автозбереження і перемикання перегляду; відновлення старої plain-text чернетки; відхилення надмірної вставки без втрати попереднього тексту.

Для друку додані API-сценарії відсутності приватних нотаток (включно зі сторонніми полями у знімку), доступу власника й конфлікту редакцій. Друк/PDF у браузері не перевірено: Docker залишався недоступним після помилки `read-only file system`. Після його відновлення перевірити багатосторінковий український текст, нумеровані списки, вибір розділів, приховані дані народження, позначку чернетки та відсутність приватних нотаток у PDF.

Інтеграція спирається на [офіційну документацію React](https://tiptap.dev/docs/editor/getting-started/install/react) та [StarterKit](https://tiptap.dev/docs/editor/extensions/functionality/starterkit).

Перед використанням перевірити на тестовій машині: введення під час повільного збереження, refresh із чернеткою, мережеву помилку та повтор, дві вкладки, ізоляцію різних акаунтів, перегляд без нотаток, відкриття консультації після видалення карти та мобільне компонування.
