# Базова адмінка ZORIA

Адреса: `/admin`. Пункт «Адміністрування» доступний у навігації акаунтам з
роллю `ADMIN`. Ім'я `admin` саме по собі не дає адміністративних прав.

## Можливості

- Пошук за username або email, 25 користувачів на сторінку.
- Перегляд дати створення, ролі та кількості карт, прогнозів, консультацій.
- Редагування username, email і ролі USER / CONSULTANT / ADMIN.
- Підтвердження зміни ролі перед збереженням.
- Журнал останніх 50 адміністративних змін: час, виконавець, дія, ID акаунта.
- Звернення користувачів про проблеми: автор, дата, опис, сторінка, фільтр
  та зміна статусу. Деталі: [FEEDBACK_UK.md](FEEDBACK_UK.md).

Вміст карт, прогнозів і консультацій та хеші паролів не повертаються.
Блокування, видалення користувачів, скидання паролів, підписки та MFA до цієї
першої версії не входять. CONSULTANT тут збережено як наявну роль, нових
функціональних привілеїв для неї не додано.

## Перший адміністратор

Спочатку зареєструйте окремий акаунт через звичайну форму. Використовуйте
унікальний довгий пароль. Потім призначте цьому акаунту роль із сервера.
Команда не змінює пароль і не створює автоматично акаунт, якого немає.
Замініть `your_username` на точний username.

Локально, після оновлення коду та запуску Docker:

```bash
docker compose exec api pnpm --filter @astroprocessor/api exec tsx src/admin/promote.ts your_username
```

На продакшені, після розгортання нового API-образу:

```bash
cd /opt/astro/deploy/vps
sudo docker compose --env-file .env -f compose.yaml exec api node apps/api/dist/admin/promote.js your_username
```

Відкрийте `/admin` під цим користувачем або оновіть сторінку для появи пункту
меню. Перевхід не обов'язковий: роль читається з бази для кожного API-запиту.
Наступних адміністраторів можна призначати через форму редагування.
CLI залишено серверним інструментом відновлення доступу; публічного endpoint
для початкового призначення ролі немає.

## Захист і цілісність

Всі `/admin/*` запити вимагають чинної авторизації та поточної ролі ADMIN
у базі, а не лише ролі в токені. Відповіді не кешуються. Збереження приймає
лише явний список полів. Username 3–50 символів, email до 160 символів.
Конфлікти унікальності повертають 409 без деталей бази даних.

Редагування перевіряє `updatedAt`: застаріла форма не перезаписує новішу
зміну. Оновлення та запис аудиту виконуються в одній Serializable-транзакції.
Не дозволено знімати власні права чи залишати систему без адміністратора.
Роль виконавця повторно перевіряється всередині транзакції. При конфлікті
одночасних змін потрібно оновити список і відкрити користувача знову.

AuditEvent зберігає значення username/email/role до і після редагування;
це персональні дані, доступ до бази й резервних копій має бути обмежений.
Паролі в аудиті відсутні. Серверні призначення мають дію
`admin.user.promote-cli`, без удаваного користувача-виконавця.

Для обліку активності додано міграцію `20261025000000_user_activity`:
nullable-поля `lastLoginAt` і `lastActiveAt` у User. Перед запуском нового API
на продакшені необхідно застосувати міграції (`prisma migrate deploy`) із нового
образу. Локальний Docker генерує Prisma Client та застосовує схему через
наявний `db:push` при перезапуску API. Для локального запуску без Docker також
потрібні `prisma:generate` та оновлення схеми.
Перед публічним використанням потрібні HTTPS і перевірка наведених сценаріїв.

## Час входу та активність

Останній вхід записується після успішної перевірки пароля. Реєстрація одразу
видає токен, тому також вважається першим входом. Невдалий логін дат не змінює.
Остання активність означає запит, для якого API підтвердив користувача через
`getOptionalAuthUser`, включно з читанням даних і перевіркою сесії. Це не
індикатор «онлайн»: читання вже завантаженої сторінки чи набір тексту без
API-запитів не фіксуються; авторизований запит може завершитися помилкою дії.

Запис активності обмежено одним оновленням на хвилину на користувача умовою
в SQL, яка працює також між кількома API-контейнерами. Час зберігається в UTC,
в адмінці показується в часовому поясі браузера. Оновити дані можна кнопкою
«Оновити». Попередня історія не відновлюється: NULL показується прочерком.
Перегляд адміністратором рядка користувача не змінює активність цього користувача.

Запис цих дат не змінює `updatedAt`, щоб не створювати хибні конфлікти
редагування. Помилка запису телеметрії не блокує вхід чи роботу, але залишає
попередження в серверному журналі. Паролі та токени в попередження не входять.

## Перевірки перед релізом

У цьому проході тести та збірка не запускалися за домовленістю з власником.
Потрібно перевірити: 401 без токена, 403 для USER і CONSULTANT; прямий PATCH
без прав; негайну втрату доступу після зниження ролі іншим адміном; пошук і
пагінацію; дублікати email/username; конфлікти двох відкритих форм; заборону
зняття власної ролі; наявність аудиту після збереження та серверного призначення.
