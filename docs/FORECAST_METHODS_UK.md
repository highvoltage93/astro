# Розділені розрахунки прогнозу

## Вибір методу

У прогностичному модулі спочатку обирається метод, потім натискається
«Порахувати». Зміна вкладки сама по собі не запускає розрахунок.

`POST /charts/forecast/preview` приймає поле `method`:

- `solar-return`: соляр і наступне повернення Сонця для меж солярного року.
- `progression`: карта повільних прогресій та активні аспекти, без календаря.
- `transits`: точні дати транзитів за обраний період.
- `overview`: соляр і лунар, без прогресій та транзитного календаря.
- `all` або відсутнє поле: попередній повний розрахунок для сумісності
  зі старими клієнтами та збереженими прогнозами.

Натальна карта розраховується для кожного методу. Необчислені одиничні
результати повертаються як `null`, список транзитів як порожній масив.

## Календар прогресій

Відкриття вкладки «Календар» надсилає окремий запит
`POST /charts/progression/calendar`. Він використовує параметри останнього
успішного прогнозу, а не незастосовані зміни форми, і повертає
`{ progression: SecondaryProgressionResult }`.

Endpoint примусово використовує `method: progression` та
`includeProgressionCalendar: true`. Інші методи не запускаються.
На цьому етапі карта та активні аспекти прогресій повторно обчислюються
разом із календарем. Розрахунок синхронний, фонової черги немає.

Завантажений календар зберігається в поточному результаті й не запитується
повторно при перемиканні внутрішніх вкладок. Після помилки доступна повторна
спроба. Відповідь старого запиту ігнорується після скидання або нового
розрахунку. Для збереження прогнозу з календарем встановлюється
`includeProgressionCalendar: true` у його параметрах.

## Точність та обмеження

Астрономічні формули, орбіси, кроки пошуку, уточнення екзакту, часові пояси
і правила релокації не змінені. Змінено лише вибір обчислюваних частин.
Прямий виклик `calculateSecondaryProgression` без `includeCalendar`
зберігає попередню поведінку: календар включено.

Календар може залишатися повільним; ця зміна усуває його очікування для
соляра та початкового перегляду прогресій, але не оптимізує сам пошук подій.
Час прискорення потребує окремих вимірювань на сервері.
