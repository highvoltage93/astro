# Звернення про проблеми

У спільній навігації є кнопка «Повідомити про проблему». Авторизований
користувач заповнює тему (3–160 символів) і опис (10–5000 символів). Після
успішного надсилання отримує номер звернення. При помилці текст залишається
у формі для повторної спроби; після перезавантаження незбережена чернетка
не відновлюється. Під час надсилання повторна кнопка й закриття заблоковані.
Нативний dialog підтримує фокус клавіатури та Escape поза надсиланням.

## Які дані зберігаються

- ID акаунта, username та email на момент надсилання.
- Тема, опис, шлях сторінки, серверний час створення й оновлення.
- Статус NEW / IN_PROGRESS / RESOLVED.
- Ключ повторного запиту, щоб повторне надсилання після втрати відповіді
  не створювало дубль.

Автор береться з перевіреної сесії на сервері, не з тіла запиту. В адмінці
відображаються також поточні username/email, якщо після звернення їх змінили.
Немає автоматичного збору параметрів URL, ID карт, токенів, IP, скриншотів,
вмісту прогнозів чи консультацій. У формі є прохання не додавати секрети
та дані клієнтів у вільний текст. Користувач сам контролює зміст опису.

## Доступ і опрацювання

`POST /feedback` доступний лише авторизованим користувачам. Ліміт: 5 нових
звернень за 10 хвилин на акаунт. Перевірка кількості та створення виконуються
в транзакції з блокуванням рядка автора, тож паралельні запити не обходять
ліміт. Повтор того самого ключа з іншим змістом повертає 409; з тим самим
змістом повертає номер уже створеного звернення і не витрачає ліміт.

У `/admin` є секція «Звернення про проблеми»: список по 25 записів, фільтр
статусу, повний опис, автор, email, дата, сторінка та ідентифікатори.
`GET /admin/feedback` та `PATCH /admin/feedback/:id` захищені тим самим
ADMIN-guard, що й керування користувачами. Звичайні користувачі не можуть
читати звернення, зокрема чужі, чи змінювати їхні статуси.

Статус змінюється явною кнопкою «Зберегти статус». Оновлення перевіряє
`updatedAt`, щоб не перезаписати новішу зміну іншого адміністратора.
Зміна статусу і аудит `admin.feedback.status` записуються в одній транзакції.
Опис у журналі аудиту не дублюється. Після видалення акаунта його звернення
видаляються каскадно. База й резервні копії містять персональні дані авторів.

Це внутрішня черга звернень, не чат: відповіді користувачу, вкладення й
email-повідомлення поки не реалізовані. Кнопки немає на сторінці входу або
друку. Час показується в часовому поясі браузера адміністратора.

## Розгортання

Додана міграція `20261025010000_feedback_reports`. Перед запуском нового API
на продакшені потрібно зробити бекап та застосувати `prisma migrate deploy`
через сервіс `migrate` із нового образу. Локальний Docker застосовує схему
під час перезапуску API через наявні prisma:generate і db:push.

Додано тести схеми вводу. Збірка, тести та браузерні перевірки не запускалися.
Перед релізом перевірити 401/403; повтори одного requestId; перевищення ліміту
паралельними запитами; збереження тексту після помилки; статуси та конфлікт
двох адмінів; відображення довгого тексту й HTML як звичайного тексту;
клавіатурне керування формою; міграцію та доступ ролі astro_app до нової таблиці.
