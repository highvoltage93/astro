# Топ астрологів: рейтинг активності

## Доступ

Сторінка `/admin/astrologers` і API `GET /admin/astrologers` доступні лише
користувачу з актуальною роллю `ADMIN`. Роль перевіряється чинною серверною
авторизацією з читанням акаунта з БД, не передається параметром клієнта.
Пункт навігації прихований для інших ролей; прямий API-запит без входу
повертає `401`, для `USER`/`CONSULTANT` — `403`.

З учасників рейтингу виключено **всіх адміністраторів**. Користувачі з нульовою
активністю залишаються в таблиці. API повертає ID, username та агреговані
лічильники, але не email, тексти консультацій, паролі чи клієнтські дані.

## Показники та формула

| Стовпець | Що рахується |
| --- | --- |
| Карти | Кількість збережених `BirthProfile` користувача |
| Прогнози | Кількість `SavedForecast` |
| Консультації | Кількість `Consultation`, включно з чернетками |
| Спостереження | Власні `KnowledgeNote`, включно з архівними |
| Опубліковані | `KnowledgePublication.published = true`, джерело не архівне |
| Бали | Карти + прогнози + консультації + власні спостереження |

Кожен збережений матеріал дає один бал. Повторні розрахунки тієї самої карти,
редакції консультацій/нотаток та активації чужих спостережень не дають додаткових
балів. Опубліковані спостереження вже включені у власні та вдруге не додаються.
Видалення матеріалу зменшує лічильник. Це поточна активність у сховищі, не
довічна статистика і не оцінка професійної якості, точності прогнозів чи репутації.

Місце обчислюється `RANK() OVER (ORDER BY score DESC)` серед усіх не-адмінів.
Однакові бали дають однакове місце; після нічиєї можливий пропуск місця.
Пошук за username та сортування за іншим стовпцем не змінюють глобальне місце.

Лічильники агрегуються окремо по кожній таблиці й лише потім приєднуються до
користувача: немає множення рядків через одночасне приєднання карт і прогнозів.
Порожні групи дають нуль. Список і загальна кількість читаються в одному
`RepeatableRead` snapshot. Нова таблиця чи поле для рейтингу не потрібні.

## Сортування й пошук

Параметри API:

- `search`: буквальний фрагмент username, без урахування регістру, до 160 символів;
- `sort`: `rank`, `username`, `score`, `charts`, `forecasts`, `consultations`,
  `observations`, `publishedObservations`;
- `direction`: `asc` / `desc`;
- `page`: 1–100000, фіксований розмір сторінки 25.

Типове сортування — бали за спаданням. В обох напрямках для рівних значень
застосовується стабільний порядок за lowercase username та ID. Пошуковий текст
передається як SQL-параметр; стовпець і напрям беруться тільки з білого списку
SQL-фрагментів. Символи `%` та `_` у пошуку не є SQL-шаблонами.

У UI всі вісім стовпців мають кнопки сортування та `aria-sort`. На телефоні
горизонтальне прокручування обмежене контейнером таблиці, а не всією сторінкою.

## Перехід до спостережень

«Переглянути» відкриває каталог з `authorId` — точним ID автора, а не пошуком
схожих імен. Назва автора в URL лише підписує фільтр і не визначає доступ.
У каталозі фільтр автора можна прибрати, також залишаються пошук за автором/назвою/тегом,
перегляд та активація конкретної редакції.

«Отримати спостереження» після підтвердження активує поточні опубліковані записи
цього автора для підказок. Така сама кнопка є в каталозі з точним фільтром автора.
За один запит додається максимум 500 нових активацій; для решти дію можна повторити.
Повторний запит не дублює записи. Приватні й архівні нотатки не додаються, зміни
вже активованих редакцій потрібно прийняти окремо. Це не автоматична підписка
на майбутні публікації автора.

Кнопка відображається за наявності опублікованих спостережень. Загальна кількість
власних спостережень у рейтингу **не дає доступу до приватних нотаток**.
Рейтинг не обходить `sharedKnowledgeUntil`: для читання/активації адміністратор
також має чинний строк доступу до каталогу. Його можна призначити в адмінці.
Автор може зняти публікацію після відкриття рейтингу; каталог перевіряє стан заново.

## Перевірка й розгортання

Додано `astrologer-ranking.test.ts`: доступ за роллю, валідація, всі напрямки
сортування, SQL-параметризація, фільтр адміністраторів та структура агрегатів.
У `knowledge-sharing.test.ts` додано перевірку точного фільтра автора.
CI підхоплює обидва через `tests/*.test.ts`.

Тести, збірка, сервер і SQL-запити до БД локально не запускалися за домовленістю.
Структурні тести SQL не замінюють перевірку реальних підсумків у PostgreSQL.
Перед випуском звірити користувача з кількома картами/прогнозами, нульові
лічильники, однакові бали, сортування між сторінками та недоступність звичайному
користувачу. Потрібна підготовлена раніше міграція спільноти
`20261114000000_shared_knowledge`; окремої міграції рейтингу немає.
